## Решения по ходу

- Шаг 6: zod только на сервере (`lib/lead/schema.ts`), форма проверяет поля через `lib/lead/rules.ts` без zod. Замер esbuild: полный zod ~25 КБ gzip, даже `zod/mini` со схемой ~10 КБ – почти весь бюджет клиентского JS (15 КБ); `rules.ts` – 0,3 КБ. Атрибуция не валит заявку: кривые поля → `null`, длинные обрезаются до 500 символов.
- Шаг 7: в одной транзакции блокировки по IP, потом по номеру (порядок фиксирован – без взаимных блокировок). Сначала дубль, потом лимит: повтор той же заявки получает 200, а не 429. Один `idempotencyKey` с разными номерами ловит `ON CONFLICT DO NOTHING`. `startedAt` в будущем (часы телефона спешат) ботом не считаем. Без `IP_HASH_SALT` в production – 500: IPv4 без соли восстанавливается перебором. Запрос без `Origin` – 403. В лог из ошибки postgres.js берём только `code` и `message`: в `parameters` лежит номер.
- Шаг 8: CTA – серверные ссылки на `#order` с `data-interest`/`data-comment`, форма ловит клики делегированием на `document`. Клиентских CTA-компонентов нет, без JS ссылка просто прокручивает к форме. Комментарий из CTA заменяет только пустое поле или текст прошлого CTA. Ошибку на blur не показываем, если пустое поле просто проскочили табом. Кнопка во время отправки `disabled`, второй запрос дополнительно режет `inFlight`. LeadForm + MobileBar с `content.ts` – ~5 КБ gzip (esbuild).
- Шаг 8: Server Action вместо `fetch` не берём – исходное задание называет `POST /api/lead` (ТЗ, раздел 2). Плюс Server Action – работа без JS – для аудитории из Instagram почти ничего не даёт, а таймаут, «Повторить» и коды 429/413/415 через `fetch` проще и уже покрыты тестами шага 7.
- Шаг 9: e2e идут через настоящий API в `kvarta_test` (не в базу из `.env.local`), сбои – через `page.route`. Чтобы тесты не мешали друг другу и не упирались в защиту: у каждого теста свой `x-forwarded-for` (лимит 5 в час) и свой номер (дедуп 10 мин), а `page.clock.setFixedTime(-10 с)` – иначе сервер считает быструю форму ботом и отвечает тихим 201 без записи. Успех доказываем повтором того же номера: 200 duplicate бывает только при записи в базу. Мобильный проект – WebKit (iPhone 13), в CI – прод-сборка через `next start`. Мутационная проверка: без защиты от двойного клика, с новым ключом на «Повторить», с плашкой поверх формы и без сдвига времени падает свой тест.
- Шаг 9: доступное имя кнопки на карточке – «Заказать : Колумбия Уила» (sr-only-спан внутри `inline-flex` становится отдельным элементом). Скринридеру не мешает, не правили. Проверку заголовков ответа главной (раздел 10) добавим в шаге 11 вместе с самими заголовками.
- Шаг 10: `notifyTelegram` в `lib/lead/telegram.ts` без Next – env и `fetch` передаются параметрами; в `route.ts` его зовёт `after()` только для новой заявки (дубли, боты, 429 не шлют). Таймаут 5 с на попытку, один повтор только при сбое сети, 429 и 5xx: 4xx («chat not found», бот удалён из группы) повтором не исправить. Ошибка в лог – без токена (он в адресе запроса). Click id без UTM в сообщении – «реклама (fbclid)», а не «прямой заход». В integration-тестах `after()` подменён очередью (`tests/integration/setup.ts`) – тест сам решает, когда выполнить задачи, и проверяет, что ответ не ждал Telegram. E2e и integration запускаются с пустыми `TELEGRAM_*`: проверили, что `@next/env` не перезаписывает пустую переменную значением из `.env.local`. Смоук на `next start` с фальшивым токеном: 201, затем `telegram_status = failed` и `HTTP 401` в логе.
